Design case study · not yet built

Sarthi — an AI chat app for Indian students and job-seekers

Planned stack: React · TypeScript · Node.js · Express · MongoDB · Server-sent events

Repo ↗

Status, honestly

Sarthi is my design-stage project. I have decided the scope, feature list and architecture below and documented them in the repository; I haven't built the application yet, so there are no usage numbers or screenshots to show. I wrote this page because the scoping decisions are the interesting engineering work so far — what I'll build, what I'll copy nothing from, and what I'll deliberately leave out.

The problem

General AI chat apps answer everyone the same way. Indian students and job-seekers ask differently: they prepare for specific exams, practise for specific interviews, paste job descriptions they are applying to, and often understand a concept best when it is explained in Hinglish. They also care what each conversation costs. I scoped Sarthi around those jobs, not around being another generic chat box.

How I chose the scope

My reference point is LibreChat, a widely used open-source AI chat application (MIT licensed, built on a MERN-style stack). I studied it the way you study any mature product: which features exist, how the architecture is organised, where the complexity lives. I'm taking feature and architecture references from it — and nothing else. The code will be my own, scoped to a fraction of LibreChat's surface, because a solo developer shipping a clone of a huge project ships nothing.

Planned architecture

  • Familiar ground: React + TypeScript frontend, Express + MongoDB backend, JWT authentication — the same stack as my other products, so the effort goes into the AI behaviour, not new plumbing.
  • Streaming answers over server-sent events, with markdown rendering in the chat UI and full conversation CRUD (create, rename, search, delete).
  • Provider adapters, not provider lock-in. Model calls sit behind small adapters (Gemini, Groq, OpenRouter — all with free tiers), so a model can be swapped or routed without touching the chat logic. API keys live server-side only, never in the browser.
  • Cost as a first-class value: every conversation tracks token usage and its approximate cost in rupees, shown to the user — the data that makes smart routing (below) possible.

The differentiators in scope

  • Resume vs job description: paste both, get a gap analysis against that specific posting.
  • Mock interview mode: the app interviews you for a role, one question at a time, and reviews your answers at the end.
  • Exam-answer modes: answers shaped the way examiners expect — structured, to the marks, instead of chat-style essays.
  • Hinglish explanations ("Samjhao"): any answer re-explained in simple Hinglish.
  • Cost-aware routing: pick the cheapest model that is good enough for the task, using the tracked per-conversation cost.

What I deliberately cut

I keep a written cut list to keep a solo project shippable. Out of scope for my v1: real retrieval-augmented search over documents, agent/tool frameworks, a code interpreter, image generation, single sign-on, and an admin panel. I named each one in the repository README as a cut, not an oversight — if Sarthi grows, they are my roadmap, in roughly that order of value.

Result so far

So far I have a scoped, documented design: an essentials list, a differentiator list, a cut list, and an architecture that reuses a proven stack with provider adapters and rupee cost tracking designed in from the start. The build comes next; I'll update this page with what actually shipped — and what changed from the plan — once it does.
