Design case study · not yet built

Sarthi — an AI chat app for Indian students and job-seekers

Planned stack: React · TypeScript · Node.js · Express · MongoDB · Server-sent events

Repo ↗

Status, honestly

Sarthi is at the design stage. The scope, feature list and architecture below are decided and documented in the repository; the application itself is not built yet, so there are no usage numbers or screenshots to show. This page exists because the scoping decisions are the interesting engineering work so far — what to build, what to copy nothing from, and what to deliberately leave out.

The problem

General AI chat apps answer everyone the same way. Indian students and job-seekers ask differently: they prepare for specific exams, practise for specific interviews, paste job descriptions they are applying to, and often understand a concept best when it is explained in Hinglish. They also care what each conversation costs. Sarthi is scoped around those jobs, not around being another generic chat box.

How the scope was chosen

The reference point is LibreChat, a widely used open-source AI chat application (MIT licensed, built on a MERN-style stack). It was studied the way you study any mature product: which features exist, how the architecture is organised, where the complexity lives. Sarthi takes feature and architecture references from it — and nothing else. The code will be original, scoped to a fraction of LibreChat's surface, because a solo developer shipping a clone of a huge project ships nothing.

Planned architecture

  • Familiar ground: React + TypeScript frontend, Express + MongoDB backend, JWT authentication — the same stack as my other products, so the effort goes into the AI behaviour, not new plumbing.
  • Streaming answers over server-sent events, with markdown rendering in the chat UI and full conversation CRUD (create, rename, search, delete).
  • Provider adapters, not provider lock-in. Model calls sit behind small adapters (Gemini, Groq, OpenRouter — all with free tiers), so a model can be swapped or routed without touching the chat logic. API keys live server-side only, never in the browser.
  • Cost as a first-class value: every conversation tracks token usage and its approximate cost in rupees, shown to the user — the data that makes smart routing (below) possible.

The differentiators in scope

  • Resume vs job description: paste both, get a gap analysis against that specific posting.
  • Mock interview mode: the app interviews you for a role, one question at a time, and reviews your answers at the end.
  • Exam-answer modes: answers shaped the way examiners expect — structured, to the marks, instead of chat-style essays.
  • Hinglish explanations ("Samjhao"): any answer re-explained in simple Hinglish.
  • Cost-aware routing: pick the cheapest model that is good enough for the task, using the tracked per-conversation cost.

What was deliberately cut

A written cut list keeps a solo project shippable. Out of scope for v1: real retrieval-augmented search over documents, agent/tool frameworks, a code interpreter, image generation, single sign-on, and an admin panel. Each is named in the repository README as a cut, not an oversight — if Sarthi grows, they are the roadmap, in roughly that order of value.

Result so far

A scoped, documented design: essentials list, differentiator list, cut list, and an architecture that reuses a proven stack with provider adapters and rupee cost tracking designed in from the start. The build comes next; this page will be updated with what actually shipped — and what changed from the plan — once it does.
