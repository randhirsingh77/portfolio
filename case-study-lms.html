Case study

Learning Management System

React · Redux Toolkit · Node.js · Express · MongoDB · Stripe · Live on Vercel + Render

Live demo ↗ Repo ↗

The problem

An online course platform has two customers with opposite needs. Instructors need to create courses, upload video lectures, price them and see how they sell. Students need to browse, buy safely, watch, and pick up exactly where they left off. Underneath both sits the part that actually matters: money and access control. A student who has not paid must never be able to watch a lecture, and a paid student must never be stuck outside a course they own.

Constraints

  • Free tiers everywhere. Frontend on Vercel, backend on Render's free tier — which sleeps when idle, a fact that ends up shaping the payment design below.
  • Real payments, safely. Stripe handles the card flow (test mode while developing); my code never touches card numbers, but it fully owns what happens after Stripe says "paid".
  • Video is heavy. Lectures are hosted on Cloudinary so neither the repo nor the database carries media files.

Architecture

  • Client: React + Redux Toolkit, with RTK Query API slices per domain (user, course, purchase, progress, media). The router separates public pages, student pages and the admin area; the footer shows only on public/student pages.
  • Server: Express (ESM) with routers mounted per domain under /api/v1/, plus helmet, a global rate limiter and input sanitisation. Models cover users, courses, lectures, purchases and per-lecture progress.
  • Access control is enforced on the server, per request. Course reads check ownership/enrolment; lecture video URLs are only returned to buyers and owners; progress endpoints answer only the enrolled student; I build public payloads field-by-field so internal data (like the list of enrolled students' IDs) never leaks into a response.
  • Payments complete through one shared helper. Stripe checkout → a completePurchase() function performs the enrolment steps. Both the Stripe webhook and the verify-on-return endpoint (below) call it, so the two paths can never drift apart, and racing them is safe because completion is idempotent.

Trade-offs I made

  • Verify-on-return in addition to the webhook. The standard design trusts the webhook alone. On a sleeping free-tier server that breaks (see below), so the success URL carries the checkout session ID back, and the progress page asks the server to confirm that session with Stripe directly — checking that the session belongs to the signed-in user before enrolling. The webhook stays as the backstop for buyers who close the tab.
  • Upload first, delete later. Profile photos and course thumbnails upload the new asset first and delete the old one only after success, saving the text edits regardless — a failed upload reports its own specific error instead of throwing away the whole edit.
  • Stateless JWT sessions. Simple and scalable; the accepted cost is that logout does not invalidate a token server-side. That is documented as a known limitation rather than hidden.

What broke

  • "Confirming your payment…" forever. After paying, the course page polled for about 10 seconds waiting for the webhook to land. But the webhook was arriving at a sleeping server that needed ~50 seconds to wake, and Stripe's retries are spaced far apart — so enrolment landed long after the page gave up. When I probed the live webhook endpoint it was healthy and fast when awake (signature verified, ~0.4s), which isolated the problem to the wake-up race. The verify-on-return design above fixed it: enrolment now lands about a second after returning from Stripe.
  • Fixes that were live in code but not on the server. For days the live site behaved as if finished fixes did not exist: the frontend redeployed on every push, but the backend service silently did not, so new UI talked to an old API (one visible symptom: instructor sign-up "failed" yet created a student account — the old server ignored the role). The lesson, now a standing rule: probe the live service and identify its deployed build before diagnosing any live bug from repository code.
  • A roster leak in a "fixed" payload. I had stripped the enrolled-students buyer-ID list from one endpoint and later found it still present in two others (course detail with status, and course-by-ID). I stripped it everywhere, replaced by a simple enrolled count.

Result

The platform is live: instructors publish courses with video lectures, students buy through Stripe and are enrolled as soon as they return, watch with tracked per-lecture progress, and admins get a dashboard with sales metrics. I verified the fixes with reproduction suites — the access-control suite went from 43/67 to 67/67 passing after my fixes, and a responsive suite passed 208/208 checks across five screen widths (360px phones to 1440px desktops).
