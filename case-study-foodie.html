Case study

Foodie — a food-delivery platform, end to end

React · TypeScript · Node.js · Express · MongoDB · Live on Render

Live demo ↗ Frontend repo ↗ Backend repo ↗

The problem

A food-delivery service is not one app — it is four, sharing one stream of orders. Customers browse a menu and order. The kitchen works a queue and controls what is in stock. Drivers pick up orders and deliver them. The owner watches sales. Most portfolio food apps stop at the menu and a cart. I built Foodie to run the whole loop: an order placed by a customer is prepared by the kitchen, picked up by a driver, tracked live by the customer, and counted in the owner's dashboard.

Constraints

  • Free hosting only. The backend runs on Render's free tier, which sleeps when idle and takes up to ~50 seconds to wake. The design has to survive that, not pretend it away.
  • No paid services. There is no budget for SMS OTPs or payment gateways, so sign-up is email/phone + password, and delivery pay is a clearly labelled demo credit.
  • One developer — me. Every feature has to be maintainable by me alone, which rules out infrastructure that needs babysitting.

Architecture

Two repositories: a React + TypeScript frontend (Zustand for state) and an Express + MongoDB backend with a proper folder structure (config / models / routes / controllers / middleware / utils).

  • The server is the money source of truth. Every order total is recomputed on the server from its own price list — a browser claiming a dish costs ₹1 still gets charged the real price. Promo rules (FOODIE50: 50% off up to ₹100 above ₹299; free delivery above ₹499 after discount) live in exactly one function on each side, and they agree.
  • Idempotent ordering. Each order carries a client-generated ID that is unique in the database; a retried submission returns the original order instead of duplicating it.
  • One lifecycle, role-checked. Orders move received → preparing → packing → on the way → delivered, and each step can only be advanced by the role that owns it (kitchen, then the assigned driver). Delivery credits the driver a ₹40 demo earning; the customer can then rate the driver, which updates a running average.
  • Live tracking by polling. The tracking screen polls every 4 seconds and interpolates the rider's position between the restaurant and the delivery point over the ride window, with an ETA while the order is on the way.
  • Its own auth. Register/login with email or phone + password (bcrypt, JWT valid 7 days), forgot/change password, and Google sign-in. Role-based dashboards for customer, admin/owner, manager and driver sit behind it.
  • A demo dataset behind the same API. The frontend talks to one typed API interface with two implementations: the real HTTP client, and a full in-browser demo dataset. Every screen works even while the free backend is asleep.

Trade-offs I made

  • Polling instead of websockets. Sockets would give smoother tracking, but free-tier services spin down and drop connections; 4-second polling is simple, honest, and survives restarts. The tracking still feels live because the rider position is interpolated between polls.
  • Own auth instead of a hosted provider. The site started on a hosted auth provider. Replacing it with my own JWT system removed a vendor dependency and a second user database to keep in sync — at the cost of owning password security, which is why passwords are bcrypt-hashed and never stored or transmitted anywhere else.
  • Server-side pricing instead of trusting the cart. Slightly more work on every order endpoint, but a tampered client can never change what it pays.

What broke

  • A header that grew until it ate the page. A script measured the fixed header's height and wrote it into a CSS variable that the header's own minimum height depended on. Each measurement made the header 1px taller, which triggered another measurement — about +1px per animation frame, forever. I fixed it by deleting the whole measuring mechanism and anchoring overlays to the header's real bottom edge at the moment they open.
  • The search panel hiding behind the header on phones. Same root cause family: the panel was positioned from a guessed header height, but on narrow phones the header wraps to two rows and is taller than the guess. Positioning from the measured edge, at open time, fixed it for every width.
  • Live tests that "failed" while everything worked. My first full live test run reported ten failed checks — all on fixed short waits, because the sleeping backend's first response took ~50 seconds. When I checked the end state in the database, every step had actually completed: the order went through kitchen and driver to delivered, and the driver was credited and rated. Lesson I took from it: on free hosting, judge a flow by its end state, not its first paint.

Result

Foodie is live and works end to end: sign up, order, watch the kitchen work the queue, track the rider on a map, get delivered, rate the driver — while the owner sees the sale in analytics. I keep the backend honest with an automated smoke suite (41 checks) that boots the real app against an in-memory database and verifies the money maths exactly — for example Pasta ×3 with FOODIE50 must total ₹650, not approximately. A keep-alive ping every 14 minutes during the day keeps the free backend awake inside its free instance hours.
